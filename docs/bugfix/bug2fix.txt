================================================================================
[CASE 01] ปรากฏการณ์ซอมบี้ค้างฟ้าและ Watchdog วนลูปไม่รู้จบ
          (Zombie Process Table Accumulation / Watchdog Hang)
================================================================================
1. อาการของบั๊ก:
   ในการรันสคริปต์ Process Supervision และ Background Job Watchdog เช่น:
   -----------------------------------------------------------------------------
   ( sleep 0.05 ) &
   bg=$!
   while kill -0 $bg 2>/dev/null; do
       sleep 0.01
   done
   echo "PROCESS_FINISHED"
   -----------------------------------------------------------------------------
   สคริปต์กลับค้างสนิท (Infinite Loop) ไม่ยอมพิมพ์คำว่า PROCESS_FINISHED
   แม้โปรเซสย่อย `sleep` จะจบการทำงานไปนานแล้วก็ตาม!

2. รากเหง้าประวัติศาสตร์ 40 ปีของ Unix / POSIX:
   ในระบบปฏิบัติการ Unix เมื่อโปรเซสลูก (Child Process) ทำงานเสร็จและเรียก `exit()`
   เคอร์เนลจะไม่ลบโครงสร้างของโปรเซสออกจาก Process Table ทันที
   แต่จะเปลี่ยนสถานะเป็น "ZOMBIE" (หรือ `<defunct>`) เพื่อเก็บ Exit Status รอให้
   โปรเซสแม่ (Parent) มารับผลลัพธ์ผ่านคำสั่ง `wait()` หรือ `waitpid()`
   คำสั่ง `kill -0 $pid` เป็นคำสั่งเช็คว่า "PID นี้ยังมีตัวตนอยู่ในตารางเคอร์เนลหรือไม่"
   ดังนั้น ตราบใดที่โปรเซสแม่ยังไม่เก็บศพ (Reap) โปรเซสลูก ซอมบี้ตัวนั้นจะยังมีตัวตนอยู่
   และ `kill -0` จะคืนค่า 0 (Success = Process Exists) ตลอดกาล!
   GNU Bash แก้ปัญหานี้ด้วยการแอบเก็บศพซอมบี้ภายในโครงสร้าง Job Table เป็นระยะ
   แต่เชลล์ทั่วไปที่สร้างใหม่มักไม่รู้เรื่องนี้ และรอ `wait` แบบ Blocking เท่านั้น

3. วิธีการแก้ปัญหาในภาษา C ของ ZBASH:
   ไฟล์: src/core/engine.c
   ฟังก์ชัน: zbash_run_line()
   ตำแหน่ง: บรรทัดต้นฟังก์ชันก่อนประมวลผลคำสั่งทุกบรรทัด
   โค้ดที่แก้ไข:
   -----------------------------------------------------------------------------
   /*
    * Non-blocking background child reaping (Zombie Exorcism)
    * ดักเก็บศพซอมบี้ที่ตายแล้วทั้งหมดในระบบอย่างไม่ขัดจังหวะการทำงาน (WNOHANG)
    * ก่อนจะเริ่มรันคำสั่งบรรทัดใหม่ทุกครั้ง
    */
   while (waitpid(-1, NULL, WNOHANG) > 0);
   -----------------------------------------------------------------------------
   ผลลัพธ์: ทันทีที่มีการเรียก `zbash_run_line()` ซอมบี้ที่ตายแล้วจะถูกล้างออกจากตารางเคอร์เนล
   ทำให้คำสั่ง `kill -0 $bg` คืนค่าข้อผิดพลาด (ESRCH: No such process) และลูปหลุดออกมาทันที!

4. บทเรียนสำหรับผู้สร้าง Shell ยุคใหม่:
   อย่าคิดว่าเมื่อโปรเซสลูกจบชีวิตแล้วมันจะหายไปจาก OS ด้วยตัวเอง
   Shell มีหน้าที่อันศักดิ์สิทธิ์ในการเป็น "สุัปเหร่อแห่งระบบปฏิบัติการ"
   ต้องมีการ Non-blocking waitpid(-1, WNOHANG) ในจุดวนลูปหลักของเชลล์เสมอ


================================================================================
[CASE 02] คำสาปทางออกและกับดัก Deadlock ใน Exit Trap
          (The Exit Trap Short-Circuit Deadlock)
================================================================================
1. อาการของบั๊ก:
   เมื่อผู้ใช้ประกาศ Trap สำหรับเหตุการณ์ EXIT และเรียกคำสั่ง `exit` เพื่อปิดเชลล์:
   -----------------------------------------------------------------------------
   trap 'echo "CLEANUP_CALLED"' EXIT
   exit 3
   -----------------------------------------------------------------------------
   เชลล์ออกจากโปรแกรมด้วยรหัส 3 ทันที แต่คำว่า "CLEANUP_CALLED" ไม่เคยถูกพิมพ์ออกมา!

2. รากเหง้าประวัติศาสตร์ 40 ปีของ Unix / POSIX:
   POSIX Standard กำหนดว่า Trap ของสัญญาณ EXIT ต้องถูกรันเมื่อเชลล์กำลังจะปิดตัว
   ไม่ว่าจะปิดตัวเพราะสคริปต์จบ หรือเพราะมีการเรียกคำสั่ง Builtin `exit`
   แต่ในสถาปัตยกรรมของเชลล์ส่วนใหญ่ `builtin_exit()` ทำงานโดยการตั้งค่าสถานะ
   `state->should_exit = true;`
   เมื่อ `builtin_exit` พยายามรันคำสั่งใน `state->exit_trap` โดยส่งให้ฟังก์ชัน
   ประมวลผลหลัก `zbash_run_line(state, trap_cmd)`
   ฟังก์ชันประมวลผลหลักกลับมีเงื่อนไขบรรทัดแรกว่า:
   `if (state->should_exit) return state->last_status;`
   ส่งผลให้คำสั่งใน Trap ถูก Short-Circuit ปฏิเสธการรันโดยอัตโนมัติ กลายเป็น Deadlock ทางตรรกะ!

3. วิธีการแก้ปัญหาในภาษา C ของ ZBASH:
   ไฟล์: src/builtins/builtins.c
   ฟังก์ชัน: builtin_exit()
   โค้ดที่แก้ไข:
   -----------------------------------------------------------------------------
   if (state->exit_trap && strlen(state->exit_trap) > 0) {
       char *trap_cmd = strdup(state->exit_trap);
       /* ปลดล็อคสถานะทางออกชั่วคราวเพื่อให้คำสั่ง Trap ทำงานได้ */
       state->should_exit = false;
       zbash_run_line(state, trap_cmd);
       free(trap_cmd);
       /* กู้คืนสถานะทางออกกลับมาอย่างสมบูรณ์ */
       state->should_exit = true;
   }
   state->exit_code = code;
   state->last_status = code;
   return code;
   -----------------------------------------------------------------------------
   ผลลัพธ์: Trap ทำงานได้อย่างราบรื่น ทำความสะอาดไฟล์ชั่วคราวเสร็จสิ้น และเชลล์ปิดตัวด้วย Exit Code 3

4. บทเรียนสำหรับผู้สร้าง Shell ยุคใหม่:
   สถานะการควบคุมการไหล (Control-Flow Flags) เช่น `should_exit`, `should_break`, `should_continue`
   เป็นดาบสองคม หากคุณแชร์ State ตัวเดียวกันระหว่างสคริปต์หลักกับ Handlers (Traps)
   คุณต้องมีกลไก Save/Restore State หรือสร้าง Sub-context สำหรับ Trap เสมอ

[CASE 03] ท่อไปป์ค้างนิรันดร์จากการรั่วไหลของ File Descriptor ใน Parent
          (The Forgotten Pipe File Descriptor Leak)
================================================================================
1. อาการของบั๊ก:
   เมื่อรันสคริปต์ที่มีการเชื่อมท่อหลายชั้น (Multi-stage Pipeline) เช่น:
   -----------------------------------------------------------------------------
   cat huge_log.txt | grep "ERROR" | wc -l
   -----------------------------------------------------------------------------
   โปรเซส `wc -l` ไม่ยอมจบการทำงาน CPU นิ่งสนิท 0% และเชลล์ไม่คืน Prompt

2. รากเหง้าประวัติศาสตร์ 40 ปีของ Unix / POSIX:
   เมื่อเชลล์สร้าง Pipeline มันจะเรียก `pipe(pipe_fds[j])` ในโปรเซสแม่
   จากนั้นทำการ `fork()` โปรเซสลูกสำหรับแต่ละคำสั่ง โดยโปรเซสลูกจะใช้ `dup2()`
   สลับท่อแล้วปิดท่อที่ไม่ใช้
   แต่ความลับของ Unix Kernel คือ: **End-of-File (EOF) จะถูกส่งไปยังปลายทางท่ออ่าน
   ก็ต่อเมื่อ "ไม่มีโปรเซสใดในทั้งระบบถือปลายท่อเขียน (Write End) เปิดค้างอยู่อีกเลย"**
   หากโปรเซสแม่ (Shell Parent) ลืมสั่ง `close(pipe_fds[j][1])` ในตัวมันเอง
   เคอร์เนลจะมองว่า "ยังมีคนเขียนอยู่ (คือตัวเชลล์แม่นั่นเอง)"
   ทำให้โปรเซสลูกตัวรับปลายทาง (`wc -l`) นั่งรอข้อมูลต่อจนหมดอายุขัย!

3. วิธีการแก้ปัญหาในภาษา C ของ ZBASH:
   ไฟล์: src/core/engine.c
   ฟังก์ชัน: zbash_execute_pipeline()
   โค้ดที่แก้ไข:
   -----------------------------------------------------------------------------
   /*
    * กฎเหล็กของ POSIX Pipeline:
    * ทันทีที่ Fork โปรเซสลูกครบทุกตัว Parent ต้องปิด Descriptor ของท่อทุกอันทันที!
    */
   for (int j = 0; j < n - 1; j++) {
       close(pipe_fds[j][0]);
       close(pipe_fds[j][1]);
   }
   /* จากนั้นค่อยทำการรอโปรเซสลูกตามปกติ */
   for (int i = 0; i < n; i++) {
       waitpid(pids[i], &status, 0);
   }
   -----------------------------------------------------------------------------

4. บทเรียนสำหรับผู้สร้าง Shell ยุคใหม่:
   ในโลกของ Unix I/O: ทรัพยากรใดที่ Parent สร้างขึ้นเพื่อส่งต่อให้ลูก
   Parent ต้องสละสิทธิ์การเป็นเจ้าของ (Relinquish Ownership) ในฝั่งของตัวเองทันทีที่ส่งมอบเสร็จ

[CASE 04] หายนะคีย์บอร์ดดับหลังลูปอ่านไฟล์
          (Terminal STDIN Destruction in Loop Redirection)
================================================================================
1. อาการของบั๊ก:
   เมื่อรันสคริปต์ที่มีการดึงไฟล์เข้าลูป `while` แล้วตามด้วยคำสั่ง `read` รอผู้ใช้:
   -----------------------------------------------------------------------------
   while read line; do
       echo "Line: $line"
   done < config.txt

   read -p "Enter Choice: " user_choice
   -----------------------------------------------------------------------------
   คำสั่ง `read` บรรทัดล่างไม่รอรับการพิมพ์จากคีย์บอร์ด แต่ข้ามผ่านไปทันทีเสมือนเจอ EOF!

2. รากเหง้าประวัติศาสตร์ 40 ปีของ Unix / POSIX:
   เมื่อลูป `while ... done < file` ทำงานในโปรเซสหลักของเชลล์
   การเปลี่ยนเส้นทาง (Redirection) จะเรียกคำสั่งระบบ `dup2(fd, STDIN_FILENO)`
   การกระทำนี้จะ **ทำลาย (Clobber) File Descriptor หมายเลข 0 ของหน้าจอเทอร์มินัลทิ้งไปอย่างถาวร**
   และแทนที่ด้วยไฟล์ `config.txt`
   เมื่อลูปอ่านจนหมดไฟล์ FD 0 จะตกอยู่ในสถานะ EOF ตลอดไป
   ทำให้คำสั่ง `read` ใดๆ หลังจากนั้นไม่สามารถติดต่อกับแป้นพิมพ์ได้อีกเลย

3. วิธีการแก้ปัญหาในภาษา C ของ ZBASH:
   ไฟล์: src/core/engine.c
   ฟังก์ชัน: zbash_run_while_loop()
   โค้ดที่แก้ไข:
   -----------------------------------------------------------------------------
   /* สำรอง Terminal STDIN เดิมไว้ก่อนเปลี่ยนทิศทาง I/O */
   int saved_in = dup(STDIN_FILENO);

   /* ใช้งาน Redirection สำหรับตัวลูป */
   apply_redirections(&loop_cmd);

   /* ประมวลผลลูปจนจบ... */

   /* กู้คืน Terminal STDIN เดิมกลับมาทันที */
   dup2(saved_in, STDIN_FILENO);
   close(saved_in);
   -----------------------------------------------------------------------------

4. บทเรียนสำหรับผู้สร้าง Shell ยุคใหม่:
   ทุกการเปลี่ยนแปลง Standard Descriptors (0, 1, 2) ในระดับ Builtin หรือ Control-flow
   ต้องเป็น Transactional I/O: "สำรองไว้ก่อนเสมอ -> เปลี่ยนแปลง -> กู้คืนกลับมาทันทีเมื่อเสร็จสิ้น"

[CASE 05] มิติซ้อนและตัวแปรท้องถิ่นทะลุข้ามมิติใน Recursive Functions
          (Recursive Function Local Scope Smashing)
================================================================================
1. อาการของบั๊ก:
   เมื่อเขียนฟังก์ชันคำนวณแบบเรียกตัวเองซ้ำ (Recursion) เช่น Factorial หรือ Fibonacci:
   -----------------------------------------------------------------------------
   fact() {
       local n=$1
       if [ "$n" -le 1 ]; then
           echo 1
           return
       fi
       local prev=$(fact $(( n - 1 )))
       echo $(( n * prev ))
   }
   fact 4
   -----------------------------------------------------------------------------
   ผลลัพธ์ออกมาเป็นตัวเลขเพี้ยน (เช่น 1 หรือ 2) แทนที่จะเป็น 24!

2. รากเหง้าประวัติศาสตร์ 40 ปีของ Unix / POSIX:
   ในระบบปฏิบัติการทั่วไป ฟังก์ชันจะมี Call Stack Frame เก็บตัวแปร Local แยกกันตาม Stack Pointer
   แต่ในสเปคของ POSIX Shell ดั้งเดิมไม่มีแนวคิดเรื่อง Call Stack ของตัวแปร
   ทุกตัวแปรถูกเก็บไว้ในตารางสิ่งแวดล้อมแบนราบ (Flat Environment Table)
   เมื่อ Bash เพิ่มคีย์เวิร์ด `local` ขึ้นมา หากเอนจินเขียนแบบมักง่ายด้วยการเรียก `setenv(name, val)`
   การประกาศ `local n=1` ในชั้นในสุด จะไปเขียนทับตัวแปร `n=4` ของฟังก์ชันชั้นนอกอย่างถาวร!

3. วิธีการแก้ปัญหาในภาษา C ของ ZBASH:
   ไฟล์: include/zbash.h และ src/core/engine.c
   โค้ดที่แก้ไข:
   การสร้าง Dynamic Local Scope Frame Stack ในระดับโครงสร้างข้อมูล:
   -----------------------------------------------------------------------------
   /* ใน include/zbash.h */
   typedef struct {
       char *name;
       char *old_val;
       bool was_set;
   } zbash_local_var_t;

   struct zbash_state {
       ...
       zbash_local_var_t local_vars[512];
       int local_var_count;
   };

   /* ใน src/core/engine.c เมื่อเข้าสู่ฟังก์ชัน */
   int saved_mark = state->local_var_count;

   /* เมื่อมีการประกาศ local name=val ให้บันทึกค่าเก่าของ name ลงบนสแตก */

   /* เมื่อออกจากฟังก์ชัน ทำการแกะสแตกถอยหลัง (Unwind LIFO) */
   while (state->local_var_count > saved_mark) {
       state->local_var_count--;
       zbash_local_var_t *entry = &state->local_vars[state->local_var_count];
       if (entry->was_set) {
           setenv(entry->name, entry->old_val, 1);
           free(entry->old_val);
       } else {
           unsetenv(entry->name);
       }
       free(entry->name);
   }
   -----------------------------------------------------------------------------

4. บทเรียนสำหรับผู้สร้าง Shell ยุคใหม่:
   Shell สมัยใหม่ไม่สามารถปฏิบัติต่อตัวแปรเสมือนตาราง Flat Map ทื่อๆ ได้อีกต่อไป
   ต้องจำลองพฤติกรรม Activation Records / Stack Frames ให้สมบูรณ์แบบ

[CASE 06] วิกฤต Inode เต็มดิสก์จากไฟล์ชั่วคราว Here-Strings
          (Here-String Inode Exhaustion)
================================================================================
1. อาการของบั๊ก:
   เมื่อรัน Stress Test สคริปต์ที่ประมวลผลข้อมูลปริมาณมากด้วย Here-Strings:

       grep "foo" <<< "$data_chunk"
   done
   -----------------------------------------------------------------------------

3. วิธีการแก้ปัญหาในภาษา C ของ ZBASH:
   ไฟล์: src/core/engine.c
   ฟังก์ชัน: zbash_execute_command()
   โค้ดที่แก้ไข:
   -----------------------------------------------------------------------------
   if (cmd->in_file) {
       /* ตรวจสอบว่าเป็นไฟล์ชั่วคราวของ Here-String หรือไม่ */
       if (strncmp(cmd->in_file, "/tmp/zbash_hs_", 14) == 0) {

       free(cmd->in_file);
       cmd->in_file = NULL;
   }
   -----------------------------------------------------------------------------

   ตัว Kernel จะยังยอมให้โปรเซสอ่านข้อมูลผ่าน FD ต่อไปจนเสร็จสิ้น

   หรือพิจารณาใช้ Anonymous Pipes / Memory Buffers แทนไฟล์ชั่วคราวบนดิสก์จริง

       }

[CASE 08] การหลอกตาของคำสั่งกำหนดค่าตัวแปรปิดบัง Exit Code
          (Subshell Exit Code Masking in Variable Assignments)
================================================================================
1. อาการของบั๊ก:
   ในการทดสอบความถูกต้องของสคริปต์ตรวจจับข้อผิดพลาด:
   -----------------------------------------------------------------------------
   res=$(false)
   echo $?
   -----------------------------------------------------------------------------
   GNU Bash จะพิมพ์ค่า: `1` (เพราะคำสั่ง `false` ล้มเหลว)
   แต่เอนจินเชลล์ทั่วไปพิมพ์ค่า: `0` (เสมือนว่าทุกอย่างสำเร็จลุล่วงด้วยดี)!

2. รากเหง้าประวัติศาสตร์ 40 ปีของ Unix / POSIX:
   นี่คือกฎเหล็กสุดประหลาดของมาตรฐาน POSIX Shell (IEEE Std 1003.1):
   - หากคำสั่งมีการระบุตัวโปรแกรมตามหลัง: เช่น `VAR=$(false) ls` -> Exit Code คือของ `ls`
   - แต่ถ้าทั้งบรรทัด **ไม่มีคำสั่งโปรแกรมใดเลย มีเพียงการกำหนดค่าตัวแปรล้วนๆ**
     เช่น `VAR=$(false)` -> Exit Code ของบรรทัดนั้น จะต้องเป็น Exit Code ของ
     Command Substitution ตัวสุดท้ายที่ถูกประเมิน!
   เอนจินส่วนใหญ่ตีความการกำหนดค่าตัวแปรว่าเป็น Statement ที่คืนค่า 0 เสมอ
   ทำให้ Silent Error นี้หลุดรอดและทำลายระบบ CI/CD นับไม่ถ้วน!

3. วิธีการแก้ปัญหาในภาษา C ของ ZBASH:
   ไฟล์: src/core/engine.c
   ฟังก์ชัน: zbash_execute_command()
   โค้ดที่แก้ไข:
   -----------------------------------------------------------------------------
   /* หากคำสั่งทั้งบรรทัดเป็นการกำหนดค่าตัวแปรล้วนๆ (cmd_offset == cmd->argc) */
   if (cmd_offset == cmd->argc) {
       /*
        * ตามมาตรฐาน POSIX: ให้คืนค่า last_status ที่เกิดจากการรัน Command Substitution
        * ในระหว่างขั้นตอนการขยายตัวแปร ห้ามคืนค่า 0 แบบตายตัว!
        */
       return state->last_status;
   }
   -----------------------------------------------------------------------------

4. บทเรียนสำหรับผู้สร้าง Shell ยุคใหม่:
   มาตรฐาน POSIX เต็มไปด้วยกฎเงื่อนไขเฉพาะ (Edge-case Nuances)
   อย่าเดาพฤติกรรมของ Shell จากตรรกะภาษาโปรแกรมทั่วไป (เช่น C หรือ Python)
   ต้องทดสอบเทียบเคียงกับมาตรฐานพฤติกรรมจริงของ POSIX เสมอ

[CASE 09] เครื่องหมายแอมเพอร์แซนด์ (&) โดนกลืนเป็นอาร์กิวเมนต์
          (Background Job Boundary Splitting)
================================================================================
1. อาการของบั๊ก:
   เมื่อรันสคริปต์คำสั่ง Background Job:
   -----------------------------------------------------------------------------
   sleep 0.1 & bg=$!; wait $bg
   -----------------------------------------------------------------------------
   คำสั่ง `sleep` เกิดข้อผิดพลาดว่า: `sleep: invalid time interval '&'`
   และระบบไม่แยกโปรเซสออกไปทำงานเบื้องหลัง!

2. รากเหง้าประวัติศาสตร์ 40 ปีของ Unix / POSIX:
   ในไวยากรณ์ของเชลล์ เครื่องหมายเซมิโคลอน (`;`) ทำหน้าที่เป็นตัวคั่นคำสั่ง (Command Separator)
   แต่เครื่องหมายแอมเพอร์แซนด์ (`&`) มีความซับซ้อนกว่านั้นมาก:
   - มันทำหน้าที่เป็น Command Terminator (เหมือนกับ `;`)
   - แต่ในเวลาเดียวกัน มันทำหน้าที่สั่งให้เอนจิน Fork โปรเซสนั้นโดย **ไม่ต้องรอ (No-Wait)**
   - และต้องบันทึก PID ของลูกลงในตัวแปรพิเศษ `$!`
   หาก Lexer แบ่งคำสั่งเฉพาะเครื่องหมาย `;` หรือ `&&` แต่ละเลย `&` เดี่ยวๆ
   ตัว `&` จะหลุดเข้าไปเป็น Argument ตัวหนึ่งของคำสั่งก่อนหน้าทันที!

3. วิธีการแก้ปัญหาในภาษา C ของ ZBASH:
   ไฟล์: src/core/engine.c
   ฟังก์ชัน: zbash_run_line()
   โค้ดที่แก้ไข:
   -----------------------------------------------------------------------------
   /* ตรวจจับตัวคั่นคำสั่งทั้ง ';' และ '&' ที่ไม่ได้อยู่ในคำพูด */
   if (line[i] == ';' || (line[i] == '&' && line[i+1] != '&' && (i == 0 || line[i-1] != '&'))) {
       bool is_bg = (line[i] == '&');
       /* แยกประโยคคำสั่งออกมาประมวลผล */
       char *sub_cmd = extract_command(...);
       if (is_bg) {
           pid_t bg_pid = fork();
           if (bg_pid == 0) {
               exit(zbash_execute(sub_cmd));
           } else if (bg_pid > 0) {
               state->last_bg_pid = bg_pid; /* บันทึกค่าลงตัวแปร $! */
           }
       } else {
           zbash_execute(sub_cmd);
       }
   }
   -----------------------------------------------------------------------------

4. บทเรียนสำหรับผู้สร้าง Shell ยุคใหม่:
   การแบ่งโทเค็น (Lexing) ในระดับโครงสร้างคำสั่ง ต้องแยกให้ออกระหว่าง
   Logical Operators (`&&`, `||`) กับ Control Terminators (`;`, `&`, `\n`)

[CASE 10] นิพจน์ซ้อน $(( ... )) พังทะลายจากวงเล็บชั้นใน
          (Arithmetic Parenthesis Nesting Depth Failure)
================================================================================
1. อาการของบั๊ก:
   เมื่อคำนวณนิพจน์คณิตศาสตร์ที่มีวงเล็บซ้อนด้านใน เช่น สูตรบิตมาสก์เครือข่าย:
   -----------------------------------------------------------------------------
   echo $(( (1 << (32 - p)) - 2 ))
   -----------------------------------------------------------------------------
   เชลล์แจ้งข้อผิดพลาดไวยากรณ์: `syntax error: unexpected token '16 - 2 ))'`

2. รากเหง้าประวัติศาสตร์ 40 ปีของ Unix / POSIX:
   ไวยากรณ์คณิตศาสตร์ของ Bash เริ่มต้นด้วย `$((` และจบด้วย `))`
   แต่ตัวสแกนข้อความ (Lexer) มักใช้วิธีค้นหาคู่ของสตริง `))` เป็นจุดจบของนิพจน์
   เมื่อเจอนิพจน์ที่มีวงเล็บซ้อนชั้นใน เช่น `(32 - p))` ตัว Lexer จะเข้าใจผิดคิดว่า
   เครื่องหมายปิดวงเล็บของ `(32 - p)` กับวงเล็บถัดไป กลายเป็นตัวปิดของ `$((` ทันที!
   ทำให้ตัดทอนนิพจน์กลางคัน และเศษสตริงที่เหลือกลายเป็นขยะไวยากรณ์

3. วิธีการแก้ปัญหาในภาษา C ของ ZBASH:
   ไฟล์: src/parser/lexer.c
   ฟังก์ชัน: zbash_expand_vars()
   โค้ดที่แก้ไข:
   -----------------------------------------------------------------------------
   /* ติดตามระดับความลึกของวงเล็บเดี่ยว (Parenthesis Depth Counter) */
   int pdepth = 1;
   size_t j = i + 3;
   while (j < len && pdepth > 0) {
       if (input[j] == '(') {
           pdepth++;
       } else if (input[j] == ')') {
           pdepth--;
           /* สิ้นสุดนิพจน์ก็ต่อเมื่อ pdepth กลายเป็น 0 และตัวถัดไปคือ ')' */
           if (pdepth == 0 && j + 1 < len && input[j + 1] == ')') {
               j += 2;
               break;
           }
       }
       j++;
   }
   -----------------------------------------------------------------------------

4. บทเรียนสำหรับผู้สร้าง Shell ยุคใหม่:
   ห้ามใช้ Pattern Matching หรือ Regex แบบ Flat ในการจับคู่โครงสร้างภาษาที่มี
   คุณสมบัติ Context-Free Grammar หรือ Recursive Nesting (เช่น วงเล็บ)
   ต้องใช้ Depth Counting หรือ Stack เสมอ

[CASE 11] ตัวเลขต่างฐาน (Base#Num) ถูกแปลงผิดเพี้ยนเป็นทศนิยม

   และหยุดอ่านทันทีเมื่อเจอเครื่องหมาย `#` (เพราะไม่ใช่ตัวเลข)
   ผลลัพธ์คือค่าถูกตัดทิ้งเหลือแค่เลขฐานข้างหน้า!

3. วิธีการแก้ปัญหาในภาษา C ของ ZBASH:
   ไฟล์: src/core/engine.c
   ฟังก์ชัน: eval_primary()
   โค้ดที่แก้ไข:
   -----------------------------------------------------------------------------
   long long val = strtoll(p, &end, 0);
   /* ดักตรวจสอบรูปแบบไวยากรณ์ BASE#NUMBER */
   if (end && *end == '#' && val >= 2 && val <= 64) {
       int base = (int)val;
       char *num_start = end + 1;
       char *num_end = num_start;
       val = strtoll(num_start, &num_end, base);
       p = num_end;
   } else {
       p = end;
   }
   -----------------------------------------------------------------------------

   ฟังก์ชันมาตรฐานของ libc (เช่น strtoll, printf) ไม่ได้ถูกออกแบบมาเพื่อรองรับ
   ไวยากรณ์เฉพาะตัวของ Shell Scripting ทั้งหมด คุณต้องครอบคลุม Grammar Layer ไว้ด้านบนเสมอ

[CASE 12] สแลชหนีหน้ากาก (\/) ระเบิดการแทนที่ข้อความ
          (Pattern Delimiter Slash Collision in Expansion)
================================================================================
1. อาการของบั๊ก:
   ในการแปลง URL หรือ Path ด้วยการแทนที่สตริง:
   -----------------------------------------------------------------------------
   path="api/v1/users"
   echo "${path//\//_}"  # ต้องการเปลี่ยน / ทุกตัวให้เป็น _
   -----------------------------------------------------------------------------
   เชลล์แสดงสตริงว่างเปล่า หรือแจ้งข้อผิดพลาด Bad Substitution!

2. รากเหง้าประวัติศาสตร์ 40 ปีของ Unix / POSIX:
   ไวยากรณ์ `${var//pattern/replacement}` ใช้เครื่องหมายสแลช `/` เป็นตัวคั่น
   ระหว่างส่วนค้นหา (Pattern) และส่วนแทนที่ (Replacement)
   แต่เมื่อผู้ใช้ต้องการค้นหาตัวสแลชเอง ผู้ใช้จะ Escape ด้วย `\/`
   หากโค้ดใช้ฟังก์ชันดั้งเดิม `strchr(expr, '/')`
   มันจะกระโดดไปจับคู่กับสแลชที่ถูก Escape อยู่ทันที ทำให้เอนจินสับสนว่า
   ตำแหน่งไหนคือตัวคั่นจริง ตำแหน่งไหนคือเนื้อหาของแพทเทิร์น!

3. วิธีการแก้ปัญหาในภาษา C ของ ZBASH:
   ไฟล์: src/parser/lexer.c
   ฟังก์ชัน: zbash_expand_vars()
   โค้ดที่แก้ไข:
   -----------------------------------------------------------------------------
   /* ตัวสแกนค้นหาตัวคั่นแบบรู้ทันการ Escape (Escape-Aware Delimiter Scanner) */
   char *delim = NULL;
   for (char *scan = pat; *scan; scan++) {
       if (*scan == '\\' && *(scan + 1)) {
           scan++; /* ข้ามอักขระที่ถูก Escape ไป ไม่นับเป็น Delimiter */
           continue;
       }
       if (*scan == '/') {
           delim = scan;
           break;
       }
   }
   -----------------------------------------------------------------------------

4. บทเรียนสำหรับผู้สร้าง Shell ยุคใหม่:
   กฎพื้นฐานของการ Parse สตริง: **"อักขระพิเศษที่อยู่หลัง Backslash จะต้องสูญเสียพลังพิเศษของมันเสมอ"**

   ทำให้วงจรรักษาสถานะ Quotes หลุดโฟกัส และส่ง `" ` ออกมาเป็นเนื้อสตริงแทนที่จะเป็นตัวปิดคำพูด!

3. วิธีการแก้ปัญหาในภาษา C ของ ZBASH:
   ไฟล์: src/parser/lexer.c
   ฟังก์ชัน: zbash_expand_vars()
   โค้ดที่แก้ไข:

   /* หากไม่เข้าข่ายชื่อตัวแปรใดๆ ให้พิมพ์ตัว $ ตัวเดียว */
   buf[out_idx++] = '$';
   /* ถอยตัวชี้กลับ (Rewind Pointer) เพื่อให้วงรอบใหญ่ประมวลผลอักขระถัดไปตามปกติ */
   i--; 
   -----------------------------------------------------------------------------

4. บทเรียนสำหรับผู้สร้าง Shell ยุคใหม่:

   /* สับเชลล์จะใช้ Fast-path ได้ ก็ต่อเมื่อไม่มีโทเค็นอื่นตามหลังมาเท่านั้น! */
   size_t k = j + 1;
   while (k < slen && isspace((unsigned char)line[k])) k++;

[CASE 15] อัลกอริทึมตัดข้อความล้มเหลวต่อมัลติไวลด์การ์ด
          (Prefix/Suffix Wildcard Globbing in Parameter Expansion)
================================================================================
1. อาการของบั๊ก:
   เมื่อตัดทอนข้อมูล /etc/passwd ด้วย Pattern ไวลด์การ์ดหลายตัว:
   -----------------------------------------------------------------------------
   line="root:x:0:0:root:/root:/bin/bash"
   echo "${line#*:*:}"
   -----------------------------------------------------------------------------
   ผลลัพธ์ที่ได้กลับกลายเป็น `root` หรือสตริงเดิม
   แทนที่จะตัดทอนส่วน `root:x:` ออกไปเหลือ `0:0:root:/root:/bin/bash`!

2. รากเหง้าประวัติศาสตร์ 40 ปีของ Unix / POSIX:
   การขยายตัวแปร `${var#pattern}` (ตัด Prefix สั้นสุด) หรือ `${var##pattern}` (ตัดยาวสุด)
   ตามมาตรฐาน POSIX ระบุว่า Pattern นั้นต้องเป็น **Shell Wildcard Pattern (Glob)**
   ไม่ใช่การค้นหาแบบธรรมดา (Literal Substring Match)

   และมองหาตัวอักษรดอกจันตัวจริง ทำให้การขยายค่าล้มเหลวโดยสมบูรณ์

3. วิธีการแก้ปัญหาในภาษา C ของ ZBASH:
   ไฟล์: src/parser/lexer.c
   ฟังก์ชัน: zbash_expand_vars()
   โค้ดที่แก้ไข:
   -----------------------------------------------------------------------------
   #include <fnmatch.h>

   /* ลูปค้นหาความยาว Prefix ที่ตรงกับแพทเทิร์นของ fnmatch */
   size_t match_len = 0;
   size_t vlen = strlen(val);
   for (size_t k = 1; k <= vlen; k++) {
       char tmp_c = val[k];
       val[k] = '\0';
       if (fnmatch(pat, val, 0) == 0) {
           match_len = k;
           if (is_shortest) break; /* ถ้าเป็น '#' เจอตัวแรกหยุดทันที */
       }
       val[k] = tmp_c;
   }
   -----------------------------------------------------------------------------

4. บทเรียนสำหรับผู้สร้าง Shell ยุคใหม่:
   POSIX Shell Pattern Matching ไม่ใช่ Regex และไม่ใช่ Substring
   แต่เป็น Globbing Engine ต้องเชื่อมต่อกับ `<fnmatch.h>` หรือสร้าง SIMD Glob Matcher เฉพาะตัว

   static bool is_valid_int(const char *s) {

   เมื่ออ่านข้อมูลด้วยคำสั่ง `read` และใช้ตัวแบ่งข้อมูล:
   -----------------------------------------------------------------------------
   IFS=":" read a b c <<< "foo::bar"
   IFS=" " read x y z <<< "foo   bar"
   -----------------------------------------------------------------------------
   ตัวแปร `b` ของชุดแรกมีค่าเป็นสตริงว่าง `""` (ถูกต้อง)
   แต่ตัวแปร `y` ของชุดล่างดันเก็บสตริงว่าง `""` ไปด้วย แทนที่จะกระโดดไปเก็บ `bar`!

2. รากเหง้าประวัติศาสตร์ 40 ปีของ Unix / POSIX:
   นี่คือหนึ่งในกฎที่ประหลาดและซับซ้อนที่สุดของ Shell:
   POSIX แบ่ง Internal Field Separator (IFS) ออกเป็นสองวรรณะ:
   (1) **IFS Whitespace** (ช่องว่าง, Tab, Newline):
       - หากตัวแบ่งเป็น Whitespace ตัวแบ่งที่อยู่ติดกันหลายตัวจะถูกรวมเป็นตัวเดียว (Coalesced)
       - Whitespace ที่อยู่หัวและท้ายจะถูกเล็มทิ้ง (Trimmed)
   (2) **Non-Whitespace IFS** (เช่น `:` หรือ `,`):
       - ตัวแบ่งแต่ละตัวถือเป็นตัวคั่นฟิลด์อย่างแท้จริง หากมีติดกันสองตัว `::`
         ฟิลด์ตรงกลางจะต้องเป็นสตริงว่าง (Empty Field) ห้ามรวมเป็นตัวเดียวเด็ดขาด!
   หากเชลล์เขียนฟังก์ชันแบ่งคำแบบเหมารวม จะทำให้ระบบ ETL, CSV, และ Config พังพินาศทันที

3. วิธีการแก้ปัญหาในภาษา C ของ ZBASH:
   ไฟล์: src/builtins/builtins.c
   ฟังก์ชัน: builtin_read()
   โค้ดที่แก้ไข:
   การแยก Branch การสแกนระหว่าง `is_ifs_space` กับ `is_ifs_nonspace` อย่างเคร่งครัด
   และเล็มช่องว่างเฉพาะหมวด IFS Whitespace เท่านั้น

4. บทเรียนสำหรับผู้สร้าง Shell ยุคใหม่:
   จงเคารพกฎความแตกต่างระหว่าง Whitespace Delimiter กับ Character Delimiter
   เพราะนี่คือเสาหลักของระบบท่อส่งข้อมูล Unix มาตลอดครึ่งศตวรรษ

[CASE 19] อาร์เรย์กระจายตัวกลายเป็นก้อนเดียว
          (Array "${arr[@]}" Multi-Argument Token Expansion)
================================================================================
1. อาการของบั๊ก:
   เมื่อส่งต่ออาร์เรย์เข้าไปในฟังก์ชันหรือคำสั่ง:
   -----------------------------------------------------------------------------
   items=("one apple" "two bananas")
   count_args() { echo "$#"; }
   count_args "${items[@]}"
   -----------------------------------------------------------------------------
   ผลลัพธ์พิมพ์ออกมาเป็น `1` หรือ `3` แทนที่จะเป็น `2`!

2. รากเหง้าประวัติศาสตร์ 40 ปีของ Unix / POSIX:
   ความแตกต่างระหว่าง `@` และ `*`:
   - `"${arr[*]}"` แปลงทุกองค์ประกอบเป็นสตริงยาวก้อนเดียว คั่นด้วยตัวอักษรแรกของ IFS (Arg count = 1)
   - `"${arr[@]}"` ขยายแต่ละองค์ประกอบเป็น **Argument แยกชิ้นกันอย่างเด็ดขาด** (Arg count = N)
   แม้ว่าองค์ประกอบนั้นจะมีช่องว่างอยู่ข้างใน เช่น `"one apple"` ก็ตาม
   เอนจินส่วนใหญ่ที่ไม่มีการแยก Lexer Expansion Stage ในระดับ AST
   มักจะแปลงตัวแปรเป็นสตริงยาวก่อน แล้วค่อยส่งให้ Tokenizer
   ทำให้ช่องว่างภายใน `"one apple"` แตกกระจายออกเป็นสองอาร์กิวเมนต์ย่อยโดยไม่ได้ตั้งใจ

3. วิธีการแก้ปัญหาในภาษา C ของ ZBASH:
   ไฟล์: src/parser/lexer.c
   ฟังก์ชัน: zbash_expand_tokens()
   โค้ดที่แก้ไข:
   -----------------------------------------------------------------------------
   /*
    * Standalone Array Expansion:
    * แทรก Array Element แต่ละตัวลงใน Argument Vector (argv) โดยตรงทีละก้อน
    * โดยไม่ผ่านกระบวนการ Word Splitting ซ้ำซ้อน
    */
   for (int e = 0; e < array_size; e++) {
       new_argv[new_argc++] = strdup(array_elements[e]);
   }
   -----------------------------------------------------------------------------

4. บทเรียนสำหรับผู้สร้าง Shell ยุคใหม่:
   Argument Passing ใน Shell ไม่ใช่การส่งข้อความธรรมดา แต่เป็นการส่ง Word Stream
   ที่ต้องรักษา Boundary ของอักขระพิเศษและเครื่องหมายคำพูดไว้อย่างเหนียวแน่น

1. อาการของบั๊ก:
   เมื่อทำการทดสอบ Parity เทียบระหว่าง GNU Bash กับ ZBASH:
   -----------------------------------------------------------------------------
   bash  -c 'echo $$' -> ได้ผลลัพธ์ 82341

   วิศวกรซอฟต์แวร์ที่สร้างชุดทดสอบ Differential Testing หลายคนยอมแพ้และคิดว่า
   "ไม่สามารถทดสอบ Parity แบบ 100% สำหรับฟีเจอร์ระดับ Process Control ได้"

3. วิธีการแก้ปัญหาใน ZBASH Test Suite:

   -----------------------------------------------------------------------------
   # แทนที่จะเทียบ echo $$ ตรงๆ ให้ทดสอบความสัมพันธ์เชิงตรรกะภายในกระบวนการ:
   run_adv_test "100" "PID Invariance and Validation" \
